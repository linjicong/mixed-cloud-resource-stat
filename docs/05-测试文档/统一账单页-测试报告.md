## 4. 发现的问题清单（按严重度排序）

### 🟡 一般级

#### BUG-1（一般）：KPI 账号数与 /bill/accounts 列表口径不一致（重复 cloud_conf 记录未去重 + 账单账号与 cloud_conf 名不匹配）

- **现象**：全区间下 `/bill/kpi` 返回 `accountTotalCount=9 / accountWithBillCount=2 / accountWithoutBillCount=7`，但同一区间 `/bill/accounts` 实际只有 **8 行**（2 行 hasBillData=true + 6 行 false）。KPI 说「7 个账号无账单」，列表却只列出 6 个无账单账号，对不上。`providers=tencent` 下同样：KPI total=5/without=4，accounts 实际 3 行/2 个无账单。
- **根因**：`BillQueryService.java:178` `accountTotalCount = confs.size()` 直接取 `cloud_conf` **原始行数**，未去重；而 `queryAccounts`(行 414+) 把 conf 合并进以 `accountKey(name, normalizeProvider(provider))` 为键的 `rowMap`，**天然去重**。实测 `cloud_conf` 有 9 行但 `DISTINCT(name,provider)` 仅 7——`tencent-lc|QCloud`、`tencent-fb|QCloud` 各重复 1 行（重复采集所致）。二者一个用 raw、一个用 dedup，必然打架。
- **叠加根因**：`accountWithBillCount` 来自 `sumByAccount` 的 `conf_name`（账单表口径，值为 `huawei`/`tencent-fb`），而 `accountTotalCount` 来自 `cloud_conf.name`。账单账号 **`huawei` 在 cloud_conf 里根本不存在**（`SELECT name='huawei'` → 0 行）。两套账号命名空间不一致，导致 `total - withBill` 的减法在跨命名空间做，语义失真。
- **复现**：
  ```
  curl "http://localhost:18080/bill/kpi?startMonth=2022-01&endMonth=2023-12"      # total=9 without=7
  curl "http://localhost:18080/bill/accounts?startMonth=2022-01&endMonth=2023-12" # rows=8, no-bill=6
  ```
- **影响面**：仅影响 KPI 卡 2「本期账号数」展示的数字，**不影响任何金额/占比/趋势/TOP**（金额链路已独立验证全对）。前端 KpiCards 与账号表若并排展示会让用户觉得数字对不上。
- **建议修法**：统一两处账号计数口径——`accountTotalCount` 也应按 `DISTINCT(name, normalizeProvider(provider))` 去重；并以「账号维度的账户全集」为分母（cloud_conf ∪ 账单实际出现的 conf_name），使 `withBill + withoutBill == total` 自洽。可让 `queryKpi` 复用 `queryAccounts` 已构造的 `rowMap` 计数，避免两套逻辑。

### ⚪ 文档化降级 / 未实装（非缺陷，但与架构设计 D6/U7 有偏差，需产品/架构确认预期）

#### OBS-1（建议）：break_down「明细补充源」未按 U7 实装，明细中永不出现 BD: 前缀行

- **现象**：架构设计 D6/U7 明确「当 fee_records 某账期无数据时，明细行可来自 break_down 并打 `amountSource=BREAK_DOWN`、id 前缀 `BD:`」。但实测 `unionBody`（Mapper XML）**只含 fee_records + resource_summary 两分支，无 break_down 分支**。查询 `2023-01`（fee 无数据、break_down 有 462 行）的 `/bill/details` → `total=0`，无任何 BD 行。`HCloudBreakDownProvider` 实现了 `toUnified`，但仅被 `countDroppedRows` 的 tencent 过滤循环旁路（huawei 直接被 `supports` 跳过），实际无任何调用方产出 BD 明细。
- **判定**：**金额链路完全正确**（break_down 不进聚合正是硬约束，已验证）。此项是「明细补充展示能力」的实装完整性问题，属需求覆盖度而非金额正确性。`AmountSourceEnum.BREAK_DOWN("BD")` 枚举、前端 `AMOUNT_SOURCE_LABEL` 均已就位，只差 XML 分支。
- **建议**：与 PM/Architect 确认本期是否需要 BD 明细补充。若需要，在 `unionBody` 增加 break_down 分支（且**仅明细查询走，不进 sumByRange/sumByMonth/sumByAccount/sumByProduct**，避免破坏隔离约束）；若本期明确不做，应在接口/文档标注「break_down 仅作未来扩展」，避免枚举与前端标签成为死代码。

### ⚪ 建议级（测试环境/非功能）

- **SUG-1**：`countDroppedRows()` 通过 `QCloudBillProvider.toUnified()` **全量 `selectList` 加载腾讯账单到内存**仅为统计一个 `droppedRowCount` 指标。当前 98 行无碍，但腾讯账单量级增大后（百万行）每个 KPI 请求会全表载入，存在性能隐患。建议改为 SQL 侧 `COUNT(*)` 统计非法账期行数。
- **SUG-2**：`BillAmountParser` 用静态 `AtomicInteger` 作全局异常计数，靠调用方 `resetAnomalyCount()` 按请求复位。并发请求下计数会互相串扰（A 请求的异常被 B 请求 reset/读到）。建议改为请求级（ThreadLocal 或把计数放进 condition/返回值）。当前接口未暴露并发压力，实测单线程正确。

> 说明：以上 BUG-1 为源码缺陷（交工程师修）；OBS-1/SUG 为完整性与健壮性建议，非金额错误。静态审查、口径核算、边界测试、前端四项核心目标均达成。
